Most <span className="kw">problems</span> integrating with this section come down to a missing `X-Workspace-Id` header, a caller's case relationship not being what a door expects, or asking for a door — a plain message thread, a cooperation trend — that has not been built yet. The list below covers what comes up most.

<AccordionGroup>
  <Accordion title="Finalize, the vault, or verify returns 409 even though my token doesn't verify at all">
    That's ordering, not a bug. On `finalize`, `vault_get`, and `verify`, `messaging-api` fetches the draft or package first and raises a `409` if it doesn't exist before it ever checks the caller's role. A bad token against a real package returns `403`; the same bad token against a package id that doesn't exist still returns `409`, because the missing-resource check runs first.
  </Accordion>
  <Accordion title="A package or draft from another workspace returns 409 instead of 404">
    Every lookup on `messaging-api` filters by `workspace_id` first. A row from another workspace fails the same existence check as a row that was never created, so it surfaces as the same `409` a genuinely missing id would, not a distinguishable `404`.
  </Accordion>
  <Accordion title="Building or finalizing a draft returns 403">
    Check the relationship, not the token's validity. Building and finalizing require the caller's verified relationship on the case to be `represented_party` or `self_represented_party`; the vault requires `representing_professional`. `messaging-api` checks this against `identity-api`'s real `/internal/verify` door, never a header the caller sets — a token that verifies fine on `identity-api` for the wrong relationship still gets `403` here.
  </Accordion>
  <Accordion title="A record I know is connected to the root is missing from the draft">
    That's a snapshot gap, not a data-loss bug. The structural ring comes from `relations-api`'s two-hop lookup and is hydrated from `evidence-api` at draft time; an edge that doesn't hydrate — a record that's been removed or is briefly unreadable — is dropped silently rather than retried or flagged. Build a new draft if you need a fresh read of what's currently connected.
  </Accordion>
  <Accordion title="Verify reports a node as skipped instead of matched">
    That's accurate, not a defect. Notes and files have no live source `verify` can re-fetch, so they're always reported `skipped`, never `checked`. A `skipped` node isn't proof it's unchanged — it means there was nothing to compare it against, which is different from a `mismatch`.
  </Accordion>
  <Accordion title="A published notification never reaches an email inbox or a phone">
    That's expected in this build. Only the `in_app` channel on `notifications-api` is real; `email` and `push` are Fakes that record what they would have sent without delivering it anywhere. Read the feed door to confirm an event landed rather than checking an inbox.
  </Accordion>
  <Accordion title="There's no endpoint for a plain message thread, a marketplace connection, or a cooperation trend">
    That's accurate, not a documentation gap. `messaging-api` has exactly one send path — the hash-verified Package flow — and its own `README.md` names conversations and marketplace connections as still ahead. Cooperation has no service door anywhere in this build; the closest real mechanism is `analysis-api`'s generic violation-finding engine, which is unscoped to messaging and already documented in the evidence and findings section. See this section's overview for exactly what exists today.
  </Accordion>
</AccordionGroup>

## Still stuck

If none of the above accounts for what you're seeing, check the relevant service's own `docs/adr/` for a decision that names the behavior deliberately before assuming it's a defect, then contact support@fairstandard.com with the workspace ID, case ID, and the exact request you sent.
