Ruled 2026-09-04, FS-983, part of the FS-982 line of work.

A worker picks up a message and holds it until its handler returns or
raises. If the handler runs longer than `reclaim_idle_ms`, another
worker's `xautoclaim` sees the message sitting idle and picks it up too
— now two workers are running the same handler on the same message at
once. Before this change, the only fix was to set `reclaim_idle_ms`
higher than any handler could ever run, which either under-protects a
handler that occasionally runs long or makes every other message wait
that same long stretch before a genuinely dead worker's message gets
rescued.

`StreamQueue.__init__` now takes `heartbeat_every_ms: int | None = None`.
When set, `_process_one` starts a background task while the handler
runs: every `heartbeat_every_ms`, it re-claims the message to the same
worker with `XCLAIM ... JUSTID`, which resets the message's idle time
back to zero. The beat stops when the handler returns or raises, before
anything is written: `_process_one` awaits the task's cancellation
first, as its very next step, before it decides whether to ack, write
an error, or check who owns the message. `run_worker` also switches to
reading and auto-claiming one message at a time (`count=1`) while a
heartbeat is configured, so a message this worker is holding never sits
behind a full batch waiting its turn to be beaten. None of this changes
when `heartbeat_every_ms` is left unset — the class behaves exactly as
it did in `0.2.0`, including skipping the ownership check entirely,
since there is no beat that could have lost a race to reclaim it.

The `JUSTID` flag is the reason this works safely: plain `XCLAIM`
increments the message's delivery count, and that count is what the
retry budget (`max_retries`) reads to decide when a message dead-letters.
If the heartbeat used plain `XCLAIM`, a handler that just runs long would
burn through its own retry budget before it ever got the chance to fail
— confirmed against Redis's own `XCLAIM` docs, which state "using this
option means the retry counter is not incremented." A handler that
raises still gets retried and, past `max_retries`, still dead-letters —
the heartbeat only ever touches idle time, never the count the retry
budget is built on. Each beat checks who owns the message and claims it
back in one atomic Redis script — a registered Lua script that reads
`XPENDING` and, only if the recorded consumer is still this one, calls
`XCLAIM ... 0 ... JUSTID` — so a competing claim can never land in the
gap between the check and the claim. If the script finds someone else
already owns the message, the beat loop stops beating rather than fight
the new owner for it. Separately, once the handler returns or raises
and the beat has stopped, `_process_one` makes that same ownership check one more time
before writing anything — if a beat's stopped-but-too-late check missed
a reclaim that happened in the gap, this second check still catches it,
and the handler's own result is thrown away instead of acked or
recorded as an error, since the reclaimer owns the message now, not
this worker. That check and the write that follows it are two commands, so a rescuer whose reclaim lands in that one round-trip gap (only possible after a stall past the reclaim window, which is what triggers a rescue) will re-run the handler, and its own ownership check will then discard its result: the same duplicate run this record already accepts for a stalled worker, never a lost message and never an ack of an unfinished handler.

The beat only fires while the handler is actually yielding control back
to the event loop — it is regular `asyncio` code sharing one thread with
everything else. A handler that blocks that thread (a long CPU loop, a
synchronous network call) freezes the heartbeat along with it, so any
genuinely blocking work inside a heartbeating handler needs to go
through `asyncio.to_thread` or an equivalent, not run inline.

Deletion test: `tests/test_streams.py::test_heartbeat_does_not_touch_the_delivery_count`
— submits one message, lets a slow, heartbeating handler raise, and
reads `times_delivered` straight from `XPENDING`; if a future change
swapped `JUSTID` for plain `XCLAIM`, this test would catch the delivery
count moving.
