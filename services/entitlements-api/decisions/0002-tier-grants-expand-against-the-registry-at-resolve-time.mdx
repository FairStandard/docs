---
title: "2. Tier grants expand against the capability registry at resolve time"
description: "Date: 2026-08-30"
---

Date: 2026-08-30

## Status

Accepted

## Context

Canon (governance.yaml `entitlement_model`) describes tiers as
"prefunded entitlement bundles" that "auto-attach" as entitlements to a
case; the tier ladder itself (governance.yaml `tier_ladder`) is
cumulative and lists which capabilities each tier includes. Two shapes
were considered for representing a tier purchase as data:

1. **Materialize at issue time** — when an org buys a tier, insert one
   `Grant` row per capability the tier currently covers.
2. **Expand at resolve time** — store one `Grant` row with `tier` set
   and no `capability_key`, and have `resolve()` consult the
   `CapabilityTier` registry to decide whether the requested capability
   falls under that tier.

Materializing at issue time means a later change to a tier's capability
list (the register is versioned and can gain capabilities) never
reaches an org that already bought the tier before that change, unless
a migration re-issues grants — silently stale, the same drift problem
ADR 0001 is written to avoid. It would also multiply one purchase into
dozens of rows for no benefit this service needs.

## Decision

A tier purchase is one `Grant` row: `tier` set to the tier name (for
example `"Advanced"`), `capability_key` null, `source="tier"`.
`resolver.resolve()` treats a tier grant as covering `capability_key`
when `tier_covers(grant.tier, tier_required)` — a plain index comparison
over the fixed, ordered `TIER_LADDER` (`resolver.py`), and
`tier_required` comes from the `CapabilityTier` registry row for the
requested capability, looked up fresh on every `resolve()` call
(`store.py`).

The registry itself (`CapabilityTier`) is seeded as data from
`capability_tier_seed.json` — a checked-in snapshot of every `id`,
`tier_required`, and `flag` field across
`platform/canon/register/features/*.yaml` (38 capabilities as of this
snapshot), generated by a one-off script, never read from the canon path
at runtime or in CI (the platform repo is read-only to this service).
`Store.ensure_seeds()` inserts any capability_key not already present,
the same idempotent-seed pattern identity-api uses for its registries.

## Consequences

A tier grant automatically covers any capability that gets added to
that tier in a future canon update, once the snapshot is regenerated and
re-seeded — no grant migration needed. The tradeoff is that
`capability_tier_seed.json` can drift from canon between snapshot
refreshes; that drift is visible (the file has a provenance header with
its generation date and file count) rather than silent, and refreshing
it is a deliberate, reviewable diff, not a runtime read of another
service's private repo.
