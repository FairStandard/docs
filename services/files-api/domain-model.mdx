The language of this service. One meaning per term.

**Format**:
The byte-level container a file is made of (CSV, PDF, PNG, ...), decided
by `detect_format` without looking at what the bytes mean. Deterministic
classification of bytes, not a judgment call.
_Avoid_: type (too broad — used for doc type too), mime type (an
implementation detail of one detection tier, not the concept)

**Doc type**:
What kind of document this is by meaning (a call history CSV, an iMessage
export, a calls report PDF...), decided by the caller before it asks this
service to extract. This service does not decide doc type — that call
stays with the caller, because it also has to decide things this service
never sees (is this actually media that belongs to media-api instead of
a document at all).
_Avoid_: classification (that word, and the decision it names, belongs to
the caller)

**Processor**:
One deterministic parser for one doc type, self-registered in the
processor registry. Turns file bytes into records plus a report of how
the parse went.
_Avoid_: extractor (reserved for the AI escalation tier, which lives in
the caller, not here)

**Record**:
One normalized fact a processor extracted (a call, a message), shaped for
delivery to an evidence store this service never talks to.
_Avoid_: item, entry

**Verdict**:
Whether an extraction should be trusted, computed the same way regardless
of which processor produced it — does the record count match what the
document claims, does every record carry its required fields.
_Avoid_: result (too broad — ExtractResponse already covers "result")

**Extraction tier**:
Deterministic parsing is the only tier this service runs. A caller whose
extraction comes back invalid decides on its own whether to escalate to
an AI reader — that decision and that model call happen outside this
service, always.
_Avoid_: escalation (that word names a capability this service does not
have)

### Platform vocabulary (ruled 2026-09-05)

These words are platform structure, shared by every context. Each is owned by
one context and defined there; use them exactly as defined and do not coin a
local synonym. Rule `finding-and-pattern-are-platform-structure` in the canon.

**Record** (owned by evidence):
Anything a case holds as evidence: a call, a message, a money movement, a
document, a recording, a photo, an export — every file type.
_Avoid_: file, item, event, upload

**Finding** (owned by analysis):
One detected event on one record: what was measured and what it is consistent
with, never a legal conclusion.
_Avoid_: violation, detection, result, verdict, conduct event

**Pattern** (owned by analysis):
A course of conduct: many findings and dated events for one party over a
period, under one category, with its own provenance, review history, and
time-ordered trail. Made by a pack's pattern rule or assembled by a person;
both have the same shape.
_Avoid_: pattern group, cluster, campaign

**Category** (pack content):
The practice-area pack's catalog of the kinds of behaviour a finding or
pattern is filed under. The platform knows there is a catalog; the pack says
what is in it.
_Avoid_: conduct category, conduct type, a hard-coded enum

**Frame** (pack content):
A named lens a pack attaches to a pattern kind — coercive control, restrictive
gatekeeping — carrying its source and its evidentiary standing. A frame
explains a pattern; it never changes what the findings measured.
_Avoid_: diagnosis, syndrome, label

**Conduct**:
Not a platform word. Texas statute uses it to name specific offences; packs
may use it inside their own content only.
_Avoid_: conduct, conduct event, conduct type (in any core module, schema, or glossary)
