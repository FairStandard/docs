The packs context holds practice-area configuration: the content that
makes the platform's screens, taxonomies, and labels different for family
law than for any other practice area, without any of that difference
being written into application code (platform DESIGN.md section 8).

## Language

**Pack**:
One published version of one practice area's configuration. Immutable
once published — a pack is never edited, only superseded by a new
version.
_Avoid_: config, settings (too generic — this is content, not app config)

**Practice area**:
A string key (`family-law`, `estate-planning`, ...) that packs are
published under. A practice area exists when it is registered in the
practice-area registry (ADR 0003) — registration comes first, publishing
requires it. Still data, never a hardcoded enum.
_Avoid_: vertical, tenant

**Section**:
One named slice of a pack's content (`lifecycle_phases`,
`legal_domain`, `analysis`, ...). New section kinds are added by
publishing content with a new key, never by changing this service's
schema — that is what "extensible data, not enums" means here.
`legal_domain` is the documented, publish-validated section for a
practice area's legal-domain structure (areas of practice, causes of
action, order/provision types, order kinds) — see ADR 0003. `analysis`
is the documented, publish-validated section for a practice area's
analysis content (regex pattern sets, thresholds, vocabularies,
financial parameters, finding templates, classifier prompt) — see ADR
0004. `finding_types` and `document_categories` were removed 2026-08-31
(ADR 0003): they were placeholder content with no ruled source and no
live consumer — those vocabularies belong to the services that
detect/label them (analysis-api, intake-api/files-api), not to a pack.
_Avoid_: field, column (sections are content, not schema)

**Order kind**:
One entry in `legal_domain.order_kinds`: a kind of order a practice
area's provisions attach to (family law: `statute`, `standing_order`,
`temporary_order`, `final_order`), carrying a `precedence` used to rank
which order wins when two orders' terms conflict. Added FS-984 (ADR
0004) as part of the legal-domain structure — same publish-validated
discipline as areas of practice and causes of action, plus two rules of
its own: keys are unique and precedence values are unique within the
list.
_Avoid_: order type (too easily confused with `order_provision_types`,
a different list entirely — a provision type is a behavior a case
recognizes, an order kind is what kind of order carries that behavior)

**Analysis section**:
The `analysis` section: a practice area's analysis content, in the same
sense that `legal_domain` is a practice area's legal-domain content.
Holds what analysis-api's detection engine, financial-forensics module,
and tier-3 classifier used to hold as Python literals — regex pattern
sets, thresholds, vocabularies, financial-scan parameters, per-finding
display templates, and the classifier's prompt text — so that
practice-area-specific analysis behavior is pack content a firm can read
and a future practice area can supply its own version of, not code baked
into one service. Added FS-984 (ADR 0004). The mandated communication
platform for a case is never analysis-section content — `platforms`
here is the list of known platform identifiers, not a statement of which
one a given case requires. The section's contract (shape validation plus
`compile_pattern_set`) lives in `pack_contract.py`, a dependency-free
module a sibling repo can import directly; every template placeholder
must name one of the canonical template facts documented there and in
README.md — the contract FS-989's detection engine commits to emitting.
_Avoid_: rules, config (this is content with the same "pack" discipline
as `legal_domain` — versioned, immutable, publish-validated — not a
knob analysis-api tunes itself)

**Pattern set**:
One named entry in `analysis.pattern_sets` (`profanity`, `threat`,
`disparaging`, `custody_schedule`, `child_support`): an explicit matching
policy, `{match, flags, patterns}`, not a bare list of regex strings. The
point is `match`, which names the join strategy — `"word"` is the only
value today, and it means `pack_contract.compile_pattern_set` joins
`patterns` into `\b(?:alt1|alt2|...)\b`, reproducing analysis-api's own
compilation exactly. A reader who only sees the `patterns` list is
missing the part of the pack that says how those strings become a regex.
_Avoid_: regex list (names the alternatives but drops the matching
policy that turns them into a working pattern)

**Wire value**:
The literal a vocabulary entry's consumer actually compares against on
the wire — `call_statuses`/`call_types`/`platforms` entries carry
`{key, wire_value, label}`, and `wire_value` is neither of the other
two. analysis-api's `engine.py` compares `call.status` against
capitalized strings (`"Unanswered"`, `"Missed"`, `"Completed"`,
`"Video"`), not the pack's lowercase `key` (`"unanswered"`, ...) and not
the human-readable `label` — these are three genuinely different
strings serving three different readers (code, the wire, a person), not
one string in three casings.
_Avoid_: key (the pack-facing name a role set or template references,
not what a consumer compares against)

**Jurisdiction name**:
One of the 50 US state names plus "District of Columbia," loaded from
`data/jurisdictions.json` via `pack_contract.load_jurisdiction_names()`.
`Store.publish` passes this set into `validate_analysis_section` as
`jurisdiction_names`, which `analysis.prompt`'s `system`/`user` text may
not hardcode (word-boundary, case-insensitive — see README.md). Scope is
US states and DC only, nothing more: this is not, and does not try to
be, state-law-api's jurisdiction registry — see ADR 0004's note on why
that data lives in a packs-owned file instead of a call to that
registry.
_Avoid_: jurisdiction (too broad — state-law-api's own jurisdiction
registry is a different, larger thing this list does not overlap with
in scope or purpose)

**Role set**:
One of the three `analysis.vocabularies` fields that says which declared
vocabulary key plays a given role, rather than the engine hardcoding
that key itself: `not_answered_statuses` (which `call_statuses` keys
count as "not answered"), `completed_status` (which one key means
"completed"), `video_call_type` (which `call_types` key means "video").
A role set always references keys declared elsewhere in the same
`vocabularies` object — it never introduces a new key of its own.
_Avoid_: flag, mapping (a role set names roles among already-declared
keys, not a boolean toggle or an arbitrary key-to-value table)

**Practice-area registry**:
The `PracticeArea` table — the source of truth for "what practice areas
exist," registered via `POST /internal/practice-areas/{key}` before any
pack can publish under that key (`store.publish` rejects an
unregistered key with a `422`). Added 2026-08-31 (ADR 0003) to close a
drift risk: before this, `packs-api`, `state-law-api`, and `learning-api`
each accepted an unvalidated `practice_area` string with no shared
source of truth. Other services validate their own `practice_area`
fields against this registry through their own `PacksReader`-style seam
(see `state-law-api`'s and `learning-api`'s own CONTEXT.md/ADRs).
_Avoid_: PracticeArea enum (it is a registry table, not a closed set)

**Version**:
A pack's position in its practice area's publish sequence, assigned by
the store starting at 1. Reading a version number always returns the
same content, forever.
_Avoid_: revision, release

**Current**:
The highest version published for a practice area. What most readers
want; a caller that needs stability instead pins a specific version
number.
_Avoid_: latest (ambiguous with "most recently touched" elsewhere on the
platform; "current" names the version-sequence position specifically)

## Not workspace-scoped

Pack content is shared platform configuration, not per-workspace data.
There is no workspace column on `Pack` and no `X-Workspace-Id` header on
any door this service exposes — every firm on the platform using the
family-law practice area reads the same family-law pack. See
`main.py`'s module docstring and ADR 0002.

### Platform vocabulary (ruled 2026-09-05)

These words are platform structure, shared by every context. Each is owned by
one context and defined there; use them exactly as defined and do not coin a
local synonym. Rule `finding-and-pattern-are-platform-structure` in the canon.

**Record** (owned by evidence):
Anything a case holds as evidence: a call, a message, a money movement, a
document, a recording, a photo, an export — every file type.
_Avoid_: file, item, event, upload

**Finding** (owned by analysis):
One detected event on one record: what was measured and what it is consistent
with, never a legal conclusion.
_Avoid_: violation, detection, result, verdict, conduct event

**Pattern** (owned by analysis):
A course of conduct: many findings and dated events for one party over a
period, under one category, with its own provenance, review history, and
time-ordered trail. Made by a pack's pattern rule or assembled by a person;
both have the same shape.
_Avoid_: pattern group, cluster, campaign

**Category** (pack content):
The practice-area pack's catalog of the kinds of behaviour a finding or
pattern is filed under. The platform knows there is a catalog; the pack says
what is in it.
_Avoid_: conduct category, conduct type, a hard-coded enum

**Frame** (pack content):
A named lens a pack attaches to a pattern kind — coercive control, restrictive
gatekeeping — carrying its source and its evidentiary standing. A frame
explains a pattern; it never changes what the findings measured.
_Avoid_: diagnosis, syndrome, label

**Conduct**:
Not a platform word. Texas statute uses it to name specific offences; packs
may use it inside their own content only.
_Avoid_: conduct, conduct event, conduct type (in any core module, schema, or glossary)
