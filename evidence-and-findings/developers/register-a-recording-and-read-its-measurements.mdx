`media-api` measures a Recording only after you register it — nothing on that service watches `evidence-api` for new audio on its own. This walks through registering one, recovering it if it fails to queue, and reading back what its measurement pass produced, including how it compares to the speaker's own <span className="kw">baseline</span>.

## Before you begin

You need the recording's `content_hash` and its `evidence_file_key` — both come back from the file's delivery through `intake-api`, or from `evidence-api`'s presigned upload door if you stored the file yourself.

1. Register the recording.

   ```bash
   curl -X POST https://media-api.internal.fairstandard.com/internal/recordings \
     -H "X-Workspace-Id: $WORKSPACE_ID" \
     -H "Content-Type: application/json" \
     -d '{
       "case_id": "'"$CASE_ID"'",
       "content_hash": "'"$CONTENT_HASH"'",
       "source_type": "voicemail",
       "evidence_file_key": "'"$FILE_KEY"'",
       "duration_seconds": 94.5
     }'
   ```

   Registration deduplicates by content hash — sending the same hash twice in one workspace returns the existing row rather than starting a second measurement pass. A successful registration enqueues the recording immediately; its `status` starts at `received`.

2. Read the recording back to confirm registration.

   ```bash
   curl https://media-api.internal.fairstandard.com/internal/recordings/$RECORDING_ID \
     -H "X-Workspace-Id: $WORKSPACE_ID"
   ```

   `status` comes back `received` once it queued. If the registration call could not queue the job at all, `status` comes back as `queue_failed` on this very first read — that recording was never stranded silently. This build does not yet run the worker that turns `received` into `measured` or `failed`, so this one read is what you need here; see "What happens next" for how a service reacts once that worker is running.

3. Recover a `queue_failed` recording, if you see one.

   ```bash
   curl -X POST https://media-api.internal.fairstandard.com/internal/recordings/$RECORDING_ID/requeue \
     -H "X-Workspace-Id: $WORKSPACE_ID"
   ```

   This re-submits the same recording and marks it `received` again. It answers `409` if the recording is not currently `queue_failed` — do not call it speculatively on a recording that is already measuring or measured.

4. Read the transcript, timeline, and deviations.

   ```bash
   curl https://media-api.internal.fairstandard.com/internal/recordings/$RECORDING_ID/transcript \
     -H "X-Workspace-Id: $WORKSPACE_ID"
   curl https://media-api.internal.fairstandard.com/internal/recordings/$RECORDING_ID/timeline \
     -H "X-Workspace-Id: $WORKSPACE_ID"
   curl https://media-api.internal.fairstandard.com/internal/recordings/$RECORDING_ID/deviations \
     -H "X-Workspace-Id: $WORKSPACE_ID"
   ```

   The transcript carries ordered speaker segments plus a full-text form. The timeline is the recording's Measurements in order — emotion vectors and prosody, never a conclusion about the speaker. Deviations compares each speaker's observation on this recording against their own baseline; a speaker with fewer than three prior observations comes back empty for that speaker, because a baseline needs that many to be meaningful.

## What happens next

`media-api` publishes a `recording.measured` event the moment a recording reaches `measured`. A service that needs to react subscribes to that event and reads the recording through media's own door, rather than polling this endpoint in a loop — `analysis-api`'s own consumer is built this way. A scheduled catch-up sweep exists as a second layer, for a service that fell behind or is starting fresh; it is not how anything is meant to learn "done" first. A recording's baseline updates automatically as a side effect of each measured recording; there is no separate call to make for that. Speaker enrollment (naming an anonymous track) is a decision this build does not expose a door for yet — every speaker read back here is already resolved, not something you enroll through this API.
